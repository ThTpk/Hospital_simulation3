# สเปกแบบจำลองโรงพยาบาล 3 มิติ — รุ่นที่ 2

เอกสารนี้คือข้อตกลงก่อนเขียนโค้ด ตัวเลขทุกตัวในนี้ตรวจซ้ำได้ด้วย `docs/capacity-check.py`
ถ้าแก้พารามิเตอร์ ให้แก้ที่สคริปต์แล้วรันใหม่ อย่าแก้ตัวเลขในตารางด้วยมือ

**ข้อความทุกอย่างในตัวแบบจำลองเป็นภาษาอังกฤษ** (ป้ายห้อง ชื่อหน่วย UI) เอกสารออกแบบชุดนี้เป็นภาษาไทย

สืบทอดจาก 2 โปรเจกต์ก่อนหน้า

- `3DSimulation_HospitalSystem` (v1) — 3D + discrete-event, routing แบบมีจุดตัดสินใจ, 10 จุดบริการ, 2 ชั้น
- `SmartHospital` — M/M/c + swimlane, 18 หน่วยคิว, 11 process เส้นทางคงที่

## 0. สิ่งที่รุ่นที่ 3 เปลี่ยนจากเอกสารฉบับนี้

เอกสารนี้เขียนไว้**ก่อน**สร้างรุ่นที่ 2 บางข้อในนี้จึงเป็นสิ่งที่ตั้งใจไว้แต่รุ่นที่ 2 ไม่ได้ทำ

**บั๊กที่แก้ในรุ่นที่ 3:** ตัวจ่ายคิวของห้องตรวจปัดจำนวนห้องของแต่ละคลินิกแยกกัน
(`round(pool.rooms × cap / 19)`) ทำให้ "เปิด 14 ห้อง" ได้จริง 12 ห้อง และ "เปิด 16 ห้อง" ได้จริง 18 ห้อง

ผลคือตัวเลขในเอกสารเก่าที่ว่า "14 ห้อง → รอ 58.0 นาที" เปลี่ยนเป็น **39.6 นาที**

## 1. เป้าหมาย

ตอบคำถามเชิงบริหาร 4 ข้อให้ได้ในแบบจำลองตัวเดียว

1. **คอขวดอยู่ที่ไหน ณ เวลาใด** — ไม่ใช่ค่าเฉลี่ยทั้งวัน แต่เห็นว่า 08:20 คอขวดคือห้องตรวจ และ 11:40 ย้ายไปห้องยา
2. **ถ้าเพิ่มคน/เครื่อง 1 หน่วยที่จุดใด คุ้มที่สุด** — เทียบผลทั้งวันบน seed เดียวกัน
3. **การกระจายนัดหมายช่วยได้แค่ไหน** — มาตรการที่ไม่ต้องจ้างคนเพิ่ม แต่ v1 ตอบไม่ได้เพราะไม่มีระบบนัด
4. **ถ้าสัดส่วนการส่งตรวจเปลี่ยน ระบบรับได้ไหม** — เช่นฤดูไข้หวัดที่ส่ง X-ray เพิ่มเท่าตัว

### ขอบเขต

อยู่ในขอบเขต: การไหลของผู้ป่วย คิว กำลังคน เตียง การเคลื่อนย้าย เวลารอ
ไม่อยู่ในขอบเขต: ผลการรักษา การวินิจฉัยโรค ความถูกต้องทางคลินิก ราคายา เวชระเบียนรายบุคคล

## 2. การตัดสินใจทางสถาปัตยกรรมข้อเดียวที่สำคัญที่สุด

v1 และ SmartHospital แทน workflow คนละแบบ และแต่ละแบบมีจุดตายของตัวเอง

|  | SmartHospital | v1 |
|---|---|---|
| วิธีแทน | เส้นทางคงที่ 11 เส้น (`route: ['REG','TRI','DOC',…]`) | ตัดสินใจทีละก้าวในฟังก์ชัน `_route()` |
| ข้อดี | วาด swimlane ได้ตรง ๆ แมป M/M/c ได้ทันที | ตอบ "ถ้าเพิ่ม pLab เป็น 0.5" ได้ |
| จุดตาย | ผู้ป่วยถูกล็อกเส้นทางตั้งแต่เกิด ปรับสัดส่วนส่งตรวจไม่ได้ | workflow ฝังอยู่ใน if/else 40 บรรทัด วาดเป็นภาพไม่ได้ ตรวจสอบไม่ได้ |

**v2 ใช้แบบที่สาม: ชุดคำสั่ง (order set) + แผนการมาเยี่ยม (encounter plan)**

ผู้ป่วยไม่ได้ถูกล็อกเส้นทาง และไม่ได้ตัดสินใจแบบ if/else กระจัดกระจาย แต่

1. ตอน **พบแพทย์** ระบบจับฉลาก *ชุดคำสั่ง* จากกฎที่ประกาศเป็นข้อมูล (`ORDER_RULES`)
2. ชุดคำสั่งนั้นถูก **คลี่เป็นลำดับจุดบริการ** ด้วยฟังก์ชันเดียว (`resolvePlan()`)
3. ลำดับที่คลี่ได้คือเส้นทางของผู้ป่วยคนนั้น ซึ่ง **เก็บไว้ดูได้ทั้งเส้น**

ผลที่ได้

- ปรับความน่าจะเป็นได้เหมือน v1 (สไลเดอร์ pLab ยังทำงาน)
- แจงนับเส้นทางที่เป็นไปได้ทั้งหมดเพื่อวาด swimlane ได้เหมือน SmartHospital — เพราะเส้นทางเป็น *ผลลัพธ์ของข้อมูล* ไม่ใช่ของ control flow
- ทดสอบได้ว่า "ผู้ป่วยที่ได้ทั้ง Lab และ X-ray ต้องพบแพทย์รอบสองเพียงครั้งเดียว" ซึ่งใน v1 เป็นบั๊กที่ต้องแก้ด้วยการย้ายตำแหน่งติดธง

```js
// โครงที่ v2 จะยึด
ORDER_RULES = [
  { when: { lane: 'opd', clinic: 'med'   }, orders: { lab: 0.52, xray: 0.10, ekg: 0.12, ct: 0.02 } },
  { when: { lane: 'opd', clinic: 'ortho' }, orders: { lab: 0.10, xray: 0.74, ct: 0.08 } },
  { when: { lane: 'er', esiAtMost: 2 },     orders: { lab: 0.92, xray: 0.60, ct: 0.35, ekg: 0.55 } },
];

// คลี่ชุดคำสั่งเป็นลำดับจุด — ตรรกะ workflow ทั้งหมดอยู่ในฟังก์ชันเดียวนี้
resolvePlan(patient) // → ['lab', 'xray', 'opd', 'pharm', 'cashier', 'exit']
```

**กฎที่ห้ามละเมิดทั้งโปรเจกต์:** `model.js` คือความจริง · `layout.js` คือพิกัด ·
ไฟล์ที่เหลือมีหน้าที่ *วาดสิ่งที่สองไฟล์นั้นบอก* เท่านั้น ห้ามมีไฟล์ไหนย้อนไปเขียนสถานะในโมเดล
(กฎนี้ยกมาจาก v1 ซึ่งทำให้ตัวเลขบน panel กับภาพ 3D ขัดแย้งกันไม่ได้ — เก็บไว้)

```
                     ┌──────────────── การจำหน่าย (disposition) ────┤
                     ▼                      ▼                        ▼
            PRC → CSH → PHA → ออก     CSH → PHA → ออก          ADM → POR → WARD/ICU
            (ทำหัตถการ)              (รับยากลับบ้าน)            (รับไว้นอน)

ประตู ER → ERT (คัดแยก ESI 1–5) → ER ──┬─ LAB/XRY/CT/EKG → กลับ ER
                                        ├─ ANE → OR → PACU → POR → ICU/WARD → ออก
                                        ├─ ADM → POR → WARD → ออก
                                        └─ CSH → PHA → ออก

ผ่าตัดนัดล่วงหน้า: REG → ANE → LAB → OR → PACU ─┬─ CSH → PHA → ออก (วันเดียวกลับ)
                                                 └─ POR → WARD → ออก
```

### 5.3 กฎชุดคำสั่งและการจำหน่าย

ความน่าจะเป็นกำหนด**แยกตามคลินิก** ค่าที่แสดงคือค่าถ่วงน้ำหนักด้วยสัดส่วนผู้ป่วยของแต่ละคลินิก
(ตรวจซ้ำได้ด้วย `docs/capacity-check.py` และ `tests/flow.test.js` พิมพ์ค่าที่โมเดลทำได้จริงออกมาเทียบ)

| กฎ | ค่าถ่วงน้ำหนัก | หมายเหตุ |
|---|---:|---|
| ส่งตรวจ Lab | 33.4% | อายุรกรรม 52% · ออร์โธ 10% · ตา 8% |
| ส่ง X-ray | 18.5% | **ออร์โธ 74%** — ตัวนี้เองที่ทำให้ต้องมีเครื่องเอกซเรย์ 5 เครื่อง ไม่ใช่ 4 |
| ส่ง EKG | 4.8% | อายุรกรรม 12% |
| ส่ง CT/MRI/US | 4.0% | ศัลยกรรม 9% |
| **ถูกส่งตรวจอย่างน้อย 1 อย่าง** | **51.2%** | → พบแพทย์เฉลี่ย **1.51 ครั้ง/ราย** |
| ทำหัตถการหลังพบแพทย์ | 10% | |
| รับไว้เป็นผู้ป่วยใน (OPD) | 5% | |
| มีใบสั่งยา | 83% | ที่เหลือจ่ายเงินแล้วกลับ |
| ER → ห้องผ่าตัด | 11% | |

**กฎการพบแพทย์รอบสอง:** ผู้ป่วยกลับไปพบแพทย์ **หนึ่งครั้งเท่านั้น** หลังชุดคำสั่งเสร็จ *ทั้งชุด*
ไม่ใช่ครั้งหนึ่งต่อการตรวจหนึ่งอย่าง — เป็นบั๊กที่ v1 เจอจริงและแก้ด้วยการย้ายตำแหน่งติดธง
v2 แก้เชิงโครงสร้างด้วยการให้ `resolvePlan()` คลี่ทั้งชุดในครั้งเดียว และต้องมีเทสต์กำกับไว้ (ข้อ 11)

### 5.4 เส้นทางที่แจงนับได้ (สำหรับ swimlane)

เส้นทางไม่ได้เขียนไว้เป็นลิสต์ แต่ **แจงนับจาก `ORDER_RULES` + `resolvePlan()`** ได้
ชุดคำสั่ง 4 แบบให้ 16 ชุดย่อย × การจำหน่าย 4 แบบ × 2 lane = เส้นทางที่เป็นไปได้ ~100 เส้น
เครื่องมือ swimlane จะเรียงตามสัดส่วนผู้ป่วยแล้ววาด **8 เส้นแรกที่ครอบคลุม ≥90% ของผู้ป่วย**
แทนการวาดทั้งหมดให้อ่านไม่รู้เรื่อง

## 11. เกณฑ์ตรวจรับ

สิ่งที่ต้องเป็นจริงเสมอ ไม่ใช่ "น่าจะถูก" — เขียนเป็นเทสต์ใน `tests/flow.test.js`

**ความถูกต้องของ workflow**

1. ผู้ป่วยที่ได้ชุดคำสั่งหลายอย่าง พบแพทย์รอบสอง **หนึ่งครั้งเท่านั้น** (บั๊กของ v1)
2. ผู้ป่วยทุกคนที่มีใบสั่งยาต้องผ่าน `CSH` ก่อนออก — ไม่มีใครออกโดยไม่จ่ายเงิน
3. `ER → OR → WARD` ต้องนับยอด admit **ครั้งเดียว** ไม่ใช่สองครั้ง (บั๊กของ v1 ที่แก้ด้วยธง `admitted`)
4. ผู้ป่วย ESI 1 ที่มาถึงต้องได้เตียง ER ภายใน 5 นาทีทุกกรณี แม้คิวเต็ม
5. ไม่มีผู้ป่วยอยู่ในสองจุดบริการพร้อมกัน และผลรวม `queue + inService + waitingResult + walking` ต้องเท่ากับจำนวนที่ยังอยู่ในระบบทุก tick

**ความสอดคล้องระหว่างโมเดลกับภาพ**

6. จำนวนเจ้าหน้าที่ที่เห็นในห้องต้องเท่ากับ `roster.js` ณ นาทีนั้น — เลื่อนสไลเดอร์แล้วต้องเห็นคนเพิ่มจริง
7. คำอธิบายสีบนหน้าเว็บต้องสร้างจากค่าสีในโค้ด ไม่ใช่พิมพ์ซ้ำ (ยกกฎจาก v1)
8. ผู้ป่วยที่นั่งต้องอยู่บนเก้าอี้พอดี — เก้าอี้และตัวคนต้องเรียก `queuePos()` ตัวเดียวกัน (บั๊กของ v1)
9. ลาก timeline กลับไปนาทีเดิมต้องได้สถานะเดิมเป๊ะ (seed คงที่)

**สมรรถนะ** (วัดจริงบน Intel integrated — `ANGLE (Intel, D3D11)` ที่ 1600×900)

10. มุมที่ใช้งานจริงส่วนใหญ่ (รายหน่วย / ราย Process) ต้องอยู่ใต้ 1,000 draw call
    — วัดได้ **591** (ในห้องเดียว) และ **769** (หนึ่งหน่วย)
11. รันจนจบวันแบบไม่วาดภาพ (สำหรับ panel เทียบผล) ต้องเสร็จภายใน 150 มิลลิวินาที
    — วัดได้ **24 มิลลิวินาที** (ไม่ใส่ผัง) และ **102 มิลลิวินาที** (ใส่ผังจริง)
12. ของซ้ำ ๆ ต้องถูกรวมเป็น InstancedMesh และของเล็กต้องดับเมื่อกล้องไกลเกินกว่าจะเห็น

**ข้อ 12 แก้จากสเปกฉบับแรก ซึ่งเขียนว่า "draw call ทั้งฉากไม่เกิน 60 ตัว"**
ตัวเลขนั้นยกมาจาก v1 ซึ่งมี 10 จุดบริการและ 2 ชั้น พอมาเป็น 73 ห้อง 4 ชั้น เตียง 214 เตียง
และเครื่องมือ 73 แบบ มันเป็นไปไม่ได้ และการดันให้ถึงจะต้องตัดเนื้อหาที่เป็นหัวใจของงานนี้ทิ้ง
สิ่งที่ทำแทนคือ

- **รวมของซ้ำเป็น InstancedMesh ทีละชั้น** ไม่ใช่ทีละห้อง — เตียงผู้ป่วยใน 200 เตียงอยู่คนละห้องกัน 8 ห้อง
  แต่ใช้ geometry และวัสดุชุดเดียวกัน รวมได้ **13,370 ชิ้น**
- **ชั้นรายละเอียดต่อแผ่น** เฟอร์นิเจอร์และป้ายห้องดับเมื่อกล้องอยู่ไกลเกิน 115 หน่วย
  เพราะที่ระยะนั้นมีดผ่าตัดเล็กกว่าหนึ่งพิกเซล แต่ยังกิน draw call เท่าเดิม
- **เปิด frustum culling กลับ** (ตอนแรกปิดไว้เพราะ instanced mesh ไม่มี bounding sphere)
  — คิดใหม่ให้ถูกแล้วมุมในห้องลดจาก 10,942 เหลือ 591 draw call
- **AO ครึ่งความละเอียด · shadow map 2048 อัปเดตทุก 3 เฟรม · pixel ratio 1:1 สำหรับ 3D**
  (panel เป็น DOM จึงคมเท่าเดิม) — ยกมาจาก `tuneForRealtime` ของ skill simulator

ผลที่วัดได้ (draw call / ล้านสามเหลี่ยม): ในห้อง **591 / 2.4** · หนึ่งหน่วย **769 / 3.2** ·
หนึ่งชั้น **1,559 / 10.3** · ทั้งโรงพยาบาล **3,563 / 27.2**
มุมทั้งโรงพยาบาลยังหนักที่สุด และเป็นจุดที่ควรแก้ต่อถ้าจะไปต่อ

**ความซื่อสัตย์ของตัวเลข**

13. ทุก panel ที่แสดงค่าเฉลี่ยต้องแสดง p50 และ p90 ด้วย — ห้ามมีที่ไหนแสดงค่าเฉลี่ยเดี่ยว ๆ
14. ตัวเลขในสเปกนี้ต้องตรงกับผลของ `docs/capacity-check.py` ถ้าไม่ตรง ถือว่าสเปกผิด ไม่ใช่สคริปต์ผิด

## 12. ข้อจำกัดที่ยอมรับ

- เป็นแบบจำลองคิวและการไหล ไม่ใช่การจำลองการรักษา ไม่มีโรค ยา หรือผลลัพธ์ทางคลินิก
- ผู้ป่วยไม่หลบกันเวลาเดิน (ไม่มี collision avoidance) — เดินตามเส้นทางสั้นสุดบนกราฟทางเดิน
- ICU และห้องคลอดจำลองเป็นเตียงที่ครองเวลา ไม่มีรายละเอียดการดูแลภายใน
- ไม่มีการส่งต่อระหว่างโรงพยาบาล (refer out)
- ค่าตั้งต้นอิงโรงพยาบาลทั่วไปขนาดกลางของไทย **ไม่ได้วัดจากโรงพยาบาลจริงแห่งใด**
  ถ้าจะใช้งานจริงต้องเปลี่ยนเป็นข้อมูลของโรงพยาบาลนั้นที่ `stations.js` และ `arrivals.js`
